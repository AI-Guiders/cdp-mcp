## Context

Плеяда работает по разным деревьям параллельно (протокол 003: один билд-слот на дерево), но хабитат обещание мульти-проекта не держит. Фактические стычки 2026-09-08:

1. **Деплой привязан к якорю сессии.** `cdp_deploy` резолвит source-репо из якоря сессии: работаешь в чужом дереве — деплой своего падает (`source_not_found`). Обещание «можно работать с разными проектами» нарушается на слое доставки.
2. **Билд-слоты — ручная очередь.** Общие bin/obj shared-деревьев (guiders-platform референсится из fsharp-, dash-spec- и cdp-mcp-цепочек) → протокол «один живой билд на дерево» держится на дисциплине линий, а не на механизме.
3. **Рестарт живого сервиса бьёт по всем.** `apply` перезапускает единственный CdpService — все мосты всех линий мигают одновременно.
4. **Якорь топчется саб-агентами.** Subagent даёт изоляцию мозга, но не рук: `cdp_open` саб-агента переанкоривает якорь всей сессии — два параллельных саб-агента на разных репо топчут друг друга.

## Decision (поэтапно, не большой взрыв)

**Форма: per-line instance profile, не VM-клон.** Свой порт + свой state-рут + свой deploy-таргет + свой worktree под строящееся дерево. Сорс — общий read-only. Живой прод-инстанс — operator-gated.

**Что НЕ виртуализируем (ткань плеяды, by design):** форум, интерком, witdb-ростер, линии-реестр — общие.

### Layer 1 — Deploy с явным путём (часы)
Payload durable-джобы несёт явный source-repo-path (не «резолв от якоря»). Убирает боль №1 без всякой виртуализации. Гоча 2026-09-08: `script=` параметр обходит резолв только при удачном якоре — правильное место правки — worker-side резолв из payload.

### Layer 2 — Per-line CdpService (пилот 2 инстанса)
- Свой порт (8771 → +N) + свой state-рут (тенант-механика ADR-0199 уже есть) + свой deploy-таргет (dual-instance self/sibling — обобщение 2 → N).
- Instancer: линия (witdb) → инстанс (порт, рут, таргет). Регистр — та же witdb, колонка instance.
- Bridge per line указывает на свой инстанс (MCP-конфиг per-line).
- Практический потолок: 2–3 инстанса (CdpService с Roslyn тяжёлый).

### Layer 3 — Ансамбль-worktree (пилот после L2)
- Per-agent junction-дерево всего `open\`: source shared read-only через junction, bin/obj — локальные per-agent.
- Сложная часть: относительные кросс-репные референсы (`../guiders-platform`) — их держит именно ансамбль-раскладка, не одиночный worktree.
- Seed: worktree-механика `csx_run_plan` (PlanScope/promote) — переиспользуем, не пишем новую.

### Сопутствующий фикс (вне слоёв)
**Якорь per-worker, не per-session**: subagent-ы получают собственный якорь (или явный repo-path на каждый инструмент), перестают топтать друг друга. Дешёвый, закрывает №4 сразу.

## Consequences

- **Плюсы**: деплой перестаёт зависеть от контекста; билд-слоты становятся механикой, а не дисциплиной; рестарт одного инстанса больше не роняет чужие мосты; саб-агенты безопасны.
- **Минусы/риски**: диск (per-agent build outputs, GB-шкала); память (N тяжёлых сервисов); сложность отладки мульти-инстанса; deploy-права на «живой» инстанс — нужен явный operator-gate, иначе вернёмся к хаосу самовольных промоутов.
- **Переиспользуем**: worktree (csx_run_plan), per-seat arm-сторы, tenant state-руты (0199), dual-instance deploy (0203), dual bridges.

## Open Questions

1. Кто и когда промоутит в живой инстанс — operator-gate через чат/кнопку? Как выглядит отказ?
2. Схема портов и регистр «линия → инстанс» — witdb-колонка или отдельный реестр?
3. Layer 3: ансамбль-junction'ы — кто их создаёт/чинит (instancer? ручная инициализация линии?)
4. Идентичность сессии вызывающей линии для армов (штамповка session в witdb при identity claim) — в этот же кусок или отдельно?

## Опыт, из которого вырос ADR (2026-09-08)

- `source_not_found` × N из-за якорного резолва деплоя; починено временно переанкором сессии.
- Wake-мисроут в двух-линейном мире (timer-армы уходили Ток) — резолв «свежайшая живая» ≠ вызыватель; unique-line guard уже в проде (`6d7e008`).
- Empty-user-turn класс (гонка run'ов) — пер-session gate уже в проде (`878fb3c`); prompt_async выпилен (слепая очередь ломала контракт вежливости).
