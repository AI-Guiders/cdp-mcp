# CDP-ADR-0209: Gatekeeper tower + self-registering service slots

**Status:** draft (обсуждение с оператором)  
**Date:** 2026-09-05  
**Extends:** ADR-0198 (sidecar/bridge), ADR-0203 (deploy gap survival), ADR-0032 (durable jobs)

## Problem

Деплой-эпопея 2026-09-04/05 вскрыла, что архитектура «один сервис на фиксированном порту 8771» делает каждый деплой аварией:

1. **Порт 8771 — синглтон-точка отказа.** Рестарт сервиса = разрыв связи на 15–90 сек. In-flight вызовы мостов умирают; MCP-клиенты (opencode) прибивают stdio-серверы на сбоях.
2. **Self-kill класс.** Воркеры/оркестраторы, запущенные из деплой-таргета, не могут остановить/заменить собственный exe (kill-tree refusal + image file lock).
3. **Киллер-дисциплина — полумера.** serviceOnly-фильтр спасает мосты при service-deploy, но не спасает от разрыва.
4. **Drift/probe-костыли в мосту** (endpoint watchers, retry windows) — попытка научить пассажиров выживать при крушении башни. Каждый особый путь инструмента (health, deploy, lifecycle) требует отдельной заплатки.
5. **Версионирование вслепую** — до fingerprint не было способа узнать, что летит.

## Decision

Разделить роли: **вышка (gatekeeper) никогда не умирает, борта сменяются.**

### 1. Отдельные мини-бинарники — по одной роли каждому (решение с оператором)

- Единственный владелец порта 8771. Стартует один раз при буте (supervisor).
- Одна функция: HTTP proxy 8771 → активный борт. Читает реестр слотов на каждый запрос (или по mtime-кэшу) — **без собственного состояния**.
- Маршрутизация: **свежайший здоровый борт** (fingerprint build_utc из healthz слота). Healthz-probe перед доверием записи.
- Не деплоится, не рестартит, не знает про деплой вообще.

### 2. Self-registering slots — борта сами о себе знают

- Слот при старте выбирает **свободный порт** (random/next-free — конфликтов нет по построению).
- Регистрируется в **witdb** (существующий durable store, тот же, что intent-workspace): коллекция `slots` → `{pid, port, sha, build_utc, last_seen}`. Никаких новых форматов персистентности.
- Слот обновляет `last_seen` раз в ~5с (heartbeat). Штатный стоп → строка удаляется. Краш → строка stale, гейткипер считает молчание >15с подозрением и перед доверием probe'ит healthz (финальный арбитр — живой ответ).
- Слоты не знают друг о друге, о мостах и о деплоях.

### 3. Деплой = «запустить ещё один процесс»

```
publish новых бит в staging dir
→ старт нового инстанса из staging (свободный порт, свежий fingerprint)
→ инстанс саморегистрируется
→ гейткипер замечает свежайший здоровый → маршрутит туда
→ старый активный дорабатывает in-flight и остаётся тёплым резервом
→ резервный борт с предыдущими битами = бесплатный rollback (поднять и всё)
```

Ноль остановок активного борта. Ноль правок конфигов. Ноль pointer-файлов. Rollback = поднять старый борт.

### 4. Мост возвращается к тупой трубе

- `CdpBridgeEndpoint` (watchers/probes/drift) — **удаляется**.
- `EnsureActiveBaseAddress`, absolute-URL резолвинг — **удаляется**.
- Бридж = HTTP → 8771, Ensure-retry остаётся только как защита от старта до поднятия вышки.
- Бридж-деплой больше не требует смерти мостов (бридж-биты меняются, но мосту всё равно — он говорит с вышкой).

## Stages

1. **Gatekeeper** (~120 строк): HttpListener 8771 → slots-registry reader → forward. Режим `--gatekeeper`.
2. **Slot registration** в CdpServiceHost: выбор свободного порта, запись/удаление slots\{pid}.json, fingerprint из AssemblyMetadata.
3. **mode=ship**: префлайт (source, build, конфиги) → publish в staging → старт слота из staging → healthz-верификация → отчёт. Промоушен в активный каталог — упраздняется за ненадобностью.
4. **Снос**: CdpBridgeEndpoint, EnsureActiveBaseAddress, serviceOnly-килл дисциплина.
5. **Слоты-пул** (Buran-обобщение): `slots` = массив в конфиге, N бортов.

## Consequences

**+** Деплой перестаёт быть событием — это запуск процесса. Ноль разрывов, ноль смертей мостов, ноль рестартов MCP.
**+** Rollback бесплатный (поднять борт со старыми битами).
**+** Мост упрощается радикально (минус весь endpoint-слой).
**+** Масштабируется до N слотов (Buran: 3+1).
**−** Гейткипер = новый обязательный процесс (SPOF — но он ~120 строк и не умеет ломаться).
**−** Слоты потребляют память в резерве (N × dotnet runtime ≈ N × ~150MB) — приемлемо для 2–3 слотов.
**−** In-flight запросы на старом борту при его смерти всё же рвутся (приемлемо: борта умирают только по нашему приказу, не по деплою).

## Alternatives (rejected / deferred)

**A. ~~Разделить бинарники~~ → ПОВЫШЕНО в Decision (решение оператора, 2026-09-05): отдельные мини-бинарники, режимный диспетч упраздняется.** Исходная формулировка: CdpGatekeeper.exe (никогда не деплоится, ~120 строк), CdpService.exe (деплоится слотами), CdpMcpBridge.exe (remount-on-change). Против: N деплой-артефактов вместо одного. За: у ролей РАЗНЫЕ жизненные циклы — деплой-таргет и вечная вышка не должны быть одним файлом. God-binary (--service/stdio/--deploy-cli/--durable-job/--gatekeeper = 5 режимов) — smell.

**B. Plugin-роли**: один хост + роли как assembly. Отложено — overengineering для текущего размера.

**C. Внешний proxy (nginx/envoy/netsh portproxy)**: не наш код, отдельная установка, admin-права для netsh. Отклонено — гейткипер должен быть нашим же само-обновляемым артефактом.

## Open questions (обсудить)

1. **Кто стартует гейткипер?** Supervisor (TerminalMcp) при буте? Отдельная служба? Автозапуск мостом (текущий ensurer-паттерн)?
2. **Реестр слотов в witdb**: коллекция vs отдельная таблица? Мульти-процессный доступ (гейткипер читает witdb сервиса-сида)?
3. **Порты**: random-free vs диапазон [8772..8790]? Если слоты в docker/remote — порт из регистрации.
4. **Бридж-деплой** под новой моделью: бридж-биты тоже слот? Или бридж остаётся remount-on-change?
5. **Первый бут**: вышка поднялась, слотов нет → 503 с Retry-After? Кто поднимает первый борт?
6. **StopService семантика**: штатный слив борта = graceful drain + удаление из реестра — нужен ли drain-timeout?
